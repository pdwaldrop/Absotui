All 3 showed the same result as the original trials - correct, uncontaminated data every time (e.g. Z started at exactly 39988s = 11:06:28, its own real resume position, not X's or Y's). 6 live trials total now, across 2 media types, 4 timing/workflow patterns, and both resumed and fresh progress states, none reproducing the reported symptom. Leaning further toward this being either a very narrow timing window none of these trials happened to hit, or not a client-side bug at all.

`bug_id: 3f729c` **(startup fixed; refresh/library-switch cost fixed 2026-08-31; `get_all_books` no longer measured as a real bottleneck)**
**Loading time**: for now, not optimized for a library with a lot of items (long start loading and refresh time). Measured and substantially improved 2026-07-29 by instrumenting `App::new` against a real 22-podcast library: startup was **17.5s**, of which ~14s was sequential N+1 HTTP - one request per item, each awaited before the next was issued. Three such loops were found and made concurrent: the per-podcast episode-list fetch in `App::new` (9.8s over 22 podcasts, ~450ms each - the single biggest cost), the per-episode progress lookup in `get_library_perso_view_pod.rs` (~230ms each), and the per-book progress lookup in `App::new`'s Continue Listening path (same shape, only hit by book libraries). All three now fan out via `futures::stream::...buffered(MAX_CONCURRENT_REQUESTS)` (8 at a time, see `src/utils/http_client.rs`). **`buffered`, never `buffer_unordered`** - results feed straight into index-aligned parallel arrays and would silently desync if they came back in completion order. Result: **17.5s → 8.4s**, verified live along with the array alignment itself (Home rows and Library→Episodes both checked at index 0 *and* a non-zero index, metadata matching the right podcast in each case). Benefits the periodic podcast refresh and `R` too, since both re-run these paths.

A second pass on 2026-07-29 then overlapped the three independent startup round-trips - the Home data (`fetch_podcast_home_data` / `get_continue_listening`), the full library listing (`get_all_books`), and the `check_update` GitHub call - with `tokio::join!`. They only ever needed `id_selected_lib`, so running them in sequence just summed their latencies (~1.8s + ~2.4s + ~0.5s); driven concurrently that phase measures a steady **1.8-2.1s**, about the slowest of the three rather than their total. (`tokio::join!` specifically, not building futures and awaiting them later - Rust futures are lazy, so an unpolled future isn't running and sequential awaits would have been exactly as slow as before.) **Startup is now ~7.0-7.6s, down from 17.5s** - measured over several runs, with array alignment re-verified after the restructure.

2026-07-29's analysis found ~5s of the remaining ~7s was the per-podcast episode-list fan-out - not worth more concurrency (raising `MAX_CONCURRENT_REQUESTS` to 16 measured no improvement over 8, confirming the server is throughput-bound), but fetched at startup purely so it's ready *if* the user opens a podcast from Library - a genuine architectural lazy-loading candidate, left for its own pass.

That pass happened 2026-07-30. `App::new()` no longer waits on the per-podcast episode-list fetch (`fetch_all_pod_ep`) at all - it's spawned as a background task returning through a `oneshot` channel, and a new `App::poll_pod_ep_fetch()` (called every render-loop iteration from `main.rs`, mirroring the existing `poll_update_uninstall_event` pattern) merges the result into `self` the moment it arrives. This is background *pre-fetch*, not true per-podcast on-demand loading - all 22 podcasts still get fetched, just no longer blocking the first render - which matters because episode data also feeds the cross-podcast episode search (`render_search_book` re-filters every frame, so it picks up results automatically once the background fetch lands, no separate invalidation needed) - true on-demand-per-open would have left podcasts never explicitly opened permanently unsearchable.

The two places that read `all_*_pod_ep[index]` directly (the Library→Episodes and Search→Episodes screen transitions, plus their `_search` array variants) needed a real readiness guard, not just an empty-Vec default: `selected_library`/`selected_search_book`'s index is bounded by lists that *don't* depend on this fetch, so it can legitimately be out of bounds against the still-empty `all_*_pod_ep` arrays before the background fetch lands - an unguarded `[index]` would panic. Both sites now check `index >= array.len()` first and show "Still loading episode lists, try again in a moment..." instead of transitioning if so.

**Startup measured 17.5s → ~4.3-4.7s** on the same 22-podcast library (book libraries, which never had this cost, measured the same ~4.3s before and after - confirmed unaffected). Verified live: the readiness guard actually fires and recovers cleanly (forced deterministically with a temporary 30s artificial delay in `fetch_all_pod_ep` - the message appeared, no panic, no broken transition, then removed before committing); Library→Episodes and Search→Episodes both still open the correct podcast's real episode list once data arrives (checked at a non-zero index too); an episode opened via the search path still plays correctly end-to-end and closes cleanly on `Q`; book-library switching and playback unaffected.

`get_all_books` at ~2.4s (a single call returning the whole library listing) is the one piece left unaddressed - needs server-side paging or a lazier Library view to improve further.

Re-measured 2026-08-31 by instrumenting `App::new` fresh against the same 22-podcast library: `get_all_books` itself is no longer the bottleneck it was (~245ms now, not ~2.4s - either the server or this specific library changed since the last measurement, not something this pass changed). Instead found a much bigger, previously-unmeasured cost: `Picker::from_query_stdio()` (asks the terminal what image protocol it supports, for cover art) took **~2s on its own** - bigger than every network round-trip in `App::new` combined. Worse, since `App::new()` re-runs on every `R` refresh and every library switch (not just true startup), that ~2s was being paid again on *every* one of those, for a value that can't actually change mid-session. Fixed by querying it once per process (a `OnceLock`) and cloning the cheap result on every subsequent `App::new()` call. Verified live: a refresh's total `App::new()` time dropped from ~3.5s to ~1.4s, with the picker query itself going from ~2s to ~20 microseconds; cover art still renders correctly afterward.

`bug_id: 6e91fa`
**Screen flash on playback start:** The whole terminal briefly blanked and repainted every time playback started (pressing `l`/Enter), and on some other transitions (`R`, library switch). Found 2026-08-31 while investigating a user report: `NEEDS_TERMINAL_CLEAR`'s `terminal.clear()` in `main.rs` (added to fix a stale-popup/missing-border bug where a background playback task's raw stdout message write left ratatui's diff cache out of sync with the physical screen) ran *after* that iteration's `terminal.draw()`, with the blocking 200ms key-event poll and a 50ms sleep sitting between the physical clear and the next draw that actually repaints - up to ~250ms of genuinely blank screen. Fixed by moving the `NEEDS_TERMINAL_CLEAR` check to right before `terminal.draw()` instead of after, so the clear and the repaint it forces happen back-to-back within the same loop iteration. Verified live by instrumenting both calls: `terminal.clear()` now takes ~350µs and the following `terminal.draw()` ~9-11ms, both well under a perceptible flash. (A tmux-based rapid-screenshot test still caught a longer blank window after this fix, but a real ghostty window plus the in-process timing showed the actual absotui-side gap is now sub-frame - tmux is known to handle terminal graphics protocols slowly, and that lag reproduces even with a trivial synthetic clear+redraw unrelated to this code path.)  
`bug_id: d19c4f`

`bug_id: 2eb9e3`
**Display:** At the launch, the app is not displayed and no error message appears (especially if you change user, quit and restart the app). Solution used to be: quit the terminal and try it again. Re-investigated 2026-07-20 after an initial pass called it "likely stale": found the actual root cause via a live repro against an isolated test config with an artificially locked sqlite db - `Database::new()` (`src/db/database_struct.rs`) silently swallowed any error from the "get default user" query (`if let Ok(result) = select_default_usr() { ... }`), treating a transient database-locked error identically to "no saved user exists." Verified live: reproduced the original silent failure by holding an exclusive lock on a scratch db during login, confirmed the fix recovers transparently once retries succeed, and confirmed the fallback error is now logged instead of silent when contention outlasts the retry budget.

`bug_id: 86384e` 
**Sync**: Rarely and especially if you open VLC to listen X, close VLC and quickly open VLC again to listen Y: the progress of X is set to 0 seconds. Fixed 2026-07-28: root cause was `current_time` (seeded from the item's resume position at session start) only ever being reassigned inside the periodic 10-trigger sync branch - if VLC was quit before that first sync (or before `fetch_vlc_data` ever got one real reading), the "closed at" position sent to the server was always that unchanged starting value, which is 0 for an item with no prior progress. Fixed across all five playback loops (`handle_l_book.rs` online/offline, `handle_l_pod_home.rs`, `handle_l_pod.rs`, `handle_l_pod_offline.rs`) with a `got_real_data` flag that skips the progress sync entirely (but still closes the session) when no real VLC data was ever observed.  
`bug_id: 06e548`

Fixed 2026-07-28: found while investigating `fc695f` below - the old `Q`-quit path (`sync_session_from_database`'s `app_quit` branch) could return without ever calling `clean_exit()` in a couple of edge cases (an sqlite read error fetching the listening session, or no session found while the `is_vlc_launched_first_time` flag wasn't `"1"`), silently hanging the app on `Q` with the terminal still in raw mode/alternate screen - a user who assumed it had frozen and killed the terminal window instead would be left with exactly this symptom. `bug_id: 6ac5d8` 
**Data loss if app crash or disgracefully quit**: If app crash, the last session is not closed. Fixed across 2026-07-28/29 in two parts. First, a related symptom found while investigating the quit path: `is_vlc_running` was never reset on startup, so a crash/kill left the app booting straight into a frozen "now playing" overlay (confirmed live: stale 3-day-old progress numbers, no real VLC process behind it) until the user next pressed play - `main.rs` now resets it on every startup. Second, the underlying issue itself: the crashed session stayed open server-side, with its last position unsynced, until the next track happened to be played. `main.rs` now closes and syncs any leftover `listening_session` row once at startup (right after `init_app_with_retry`, so the server is known reachable). `bug_id: dd9a649`
**Listening Session:** Sometimes, the session (that you can see in `yourserveraddress/audiobookshelf/config/sessions`) does not close correctly, especially if you open VLC, quit it quickly, and start another book. Fixed 2026-07-28: found while setting up a repro for `9bacac` - every track switch called the close-session API *twice* for the outgoing item: once from its own natural VLC-quit-detection loop (which already closes/syncs itself the moment it notices VLC died), and once more, unconditionally, from the `'l'` handler's defensive "in case the app crashed" close - which only actually needs to run the very first time a track is played in a fresh process (that's the only point a stale, never-closed row could exist; every normal exit after that already closes what it leaves behind). `wait_prev_session_finished` now reports whether this was that first launch, and the defensive close only runs then. Verified live via tmux: captured the pre-fix double-close (two separate "Session successfully closed" log lines for the same item, ~1s apart) across 3 trials, and confirmed post-fix exactly one close happens per switch.  
`bug_id: e0b61c`
**VLC:** `VLC` continue to run after the app is quit. Fixed 2026-07-28: found alongside `fc695f` below - the `Q` quit path called `quit_vlc()` (VLC's RC "shutdown" command) but, unlike every other place in the codebase that quits VLC, never paired it with a `pkill_vlc()` fallback, so a shutdown command that didn't land (closed connection, VLC busy) left VLC running with nothing to kill it. `bug_id: fc695f`
**Listening session:** The session (that you can see in `yourserveraddress/audiobookshelf/config/sessions`) does not close when the app is quit. Fixed 2026-07-28: root cause was a race between pressing `Q` and the already-running playback loop's own VLC-quit detection (`handle_l_book.rs`/`handle_l_pod_home.rs`/`handle_l_pod.rs`) - both independently called the close-session API for the same session, and `Q`'s unconditional `process::exit(0)` could kill the loop task mid-cleanup before its own close/sync calls (or the trailing progress push) finished. Fixed by having `Q` (`quit_app` in `sync_session_from_database.rs`) defer to the already-running loop task instead of racing it: it just makes VLC die and waits for that task's own completion signal (`is_loop_break`, the same flag `wait_prev_session_finished` already waits on before a new track starts) before exiting, only closing the session itself when nothing else is watching it. Verified live via tmux: captured the pre-fix race (two separate "Session successfully closed" log lines ~250ms apart, and the loop task's own trailing "VLC closed"/"Item closed" lines never printing, cut off by exit) and confirmed post-fix the sequence is single-owner, with exit only happening after the loop task's full cleanup completes.

`bug_id: fe4116` **(fixed, unverified on real macOS)**
**cvlc macOS:** `cvlc` option is not available for now in macOS. Root cause found and fixed 2026-07-30: [app.rs](src/app.rs) unconditionally overwrote `start_vlc_program` to the VLC.app path on macOS *after* reading the `cvlc` config setting, discarding it - `cvlc` is config-file-only (no in-app Settings toggle), so a macOS user following `config.example.toml`'s own comment would set `cvlc = "0"` and see no change. Separately: `-I dummy` (the flag suppressing VLC's normal interface) was unconditional on every platform regardless of `cvlc`, so even Linux's `cvlc = "0"` never actually showed a GUI window - the binary-name distinction (`vlc` vs `cvlc`) was close to vestigial.

Fixed by threading the already-existing but unused `App.is_cvlc` field through every `start_vlc`/`spawn_track_vlc` call site (mirroring how `is_cvlc_term` already flows) and gating `-I dummy` on it in `start_vlc.rs`, instead of inferring headless-ness from platform or binary name. `cvlc = "1"` now means headless everywhere (unchanged default behavior); `cvlc = "0"` now means a real, visible VLC window everywhere, including macOS, where the launched binary is still always VLC.app (there's no separate cvlc binary to select) but whether `-I dummy` accompanies it now depends on the setting, not the platform.

Verified live on Linux with a real Wayland display (`niri msg windows`): `cvlc = "1"` still launches fully headless, no window, `-I dummy` present in the process args - unchanged from before. `cvlc = "0"` launches a real VLC window (confirmed by title: "\<episode title\> - VLC media player", no `-I dummy` in the process args), with the app's own RC control still fully functional alongside it - progress polling, pause/resume via the integrated player's Space key, and a clean single-close `Q` quit (VLC process and window both gone, no leftovers) all confirmed working with the window open. **Not verified on actual macOS hardware** - the fix is symmetric with the already-proven Linux path (same `is_cvlc` gate, same `-I dummy`/no-`-I dummy` mechanism, VLC.app is the same underlying VLC engine), but no bug label should claim "verified" for a platform this session has no access to.
